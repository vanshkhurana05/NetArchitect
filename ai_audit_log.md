## Audit Entry 1: Upward Prefix Scan Hallucination in Bitwise VLSM Allocator

### 1. Context & Original Prompt
**Prompt Given to AI:**
> "Write a TypeScript function `hostsToPrefix(hosts: number): number` that takes a required host count and returns the prefix length using bitwise operations."

### 2. Flawed Code Generated by AI
```typescript
// AI-GENERATED BUGGY CODE
export function hostsToPrefix(hosts: number): number {
  if (hosts <= 0) return -1;
  // AI attempted to find the first prefix whose capacity satisfies hosts
  for (let p = 0; p <= 32; p++) {
    const capacity = 2 ** (32 - p) - 2;
    if (capacity >= hosts) {
      return p; // FATAL ERROR: Returns p = 0 on the very first iteration!
    }
  }
  return -1;
}
```

### 3. Technical & Algorithmic Analysis: Why It Was Wrong
In IPv4 CIDR notation, **smaller prefix values represent larger address blocks**:
- A `/0` network contains $2^{32} - 2 = 4,294,967,294$ usable addresses.
- A `/24` network contains $2^{8} - 2 = 254$ usable addresses.

When scanning prefix length upwards starting at $p = 0$, the condition `capacity >= hosts` is satisfied on the **very first iteration** ($p = 0$) for *any* requested host count (e.g. 50 hosts $< 4.2\times 10^9$). As a result:
- A demand for 50 hosts returned a `/0` prefix ($4.29$ billion addresses).
- The very first carved subnet consumed the entire IPv4 address space, immediately triggering an `AddressSpaceExhaustedError` on the second subnet request and collapsing the VLSM engine.

### 4. Detection Method
Detected by automated unit tests in `tests/unit/vlsm/bits.test.ts` during boundary evaluation:
```typescript
expect(hostsToPrefix(50)).toBe(26); // AI code returned 0 instead of 26
```

### 5. Corrected Implementation
The prefix search must scan **downward from `/32` to `/0`** so that the *smallest* address block (highest prefix number) that can accommodate the requested hosts is chosen, eliminating address wastage. Furthermore, RFC 3021 semantics must be applied for point-to-point links:
```typescript
// REMEDIATED PRODUCTION IMPLEMENTATION (src/engines/vlsm/bits.ts)
export function hostsToPrefix(hosts: number): number {
  if (!Number.isFinite(hosts) || hosts <= 0) return -1;
  if (hosts <= 1) return 32; // Host route / loopback
  if (hosts === 2) return 31; // RFC 3021 point-to-point (2 usable addresses)

  // Walk downward from /32 to find the tightest fitting block
  for (let p = 32; p >= 0; p--) {
    if (usableCapacity(p) >= hosts) return p;
  }
  return -1;
}
```

### 6. Verification & Test Evidence
Validated in `tests/unit/vlsm/bits.test.ts` and `tests/unit/vlsm/allocator.test.ts`:
- 2 hosts $\rightarrow$ `/31` (RFC 3021).
- 20 hosts $\rightarrow$ `/27` ($30$ usable hosts).
- 50 hosts $\rightarrow$ `/26` ($62$ usable hosts).
- 100 hosts $\rightarrow$ `/25` ($126$ usable hosts).
- 650 hosts $\rightarrow$ `/22` ($1022$ usable hosts).

## Audit Entry 2: Unconstrained Switchport Trunking & Default Native VLAN Exposure

### 1. Context & Original Prompt
**Prompt Given to AI:**
> "Generate Cisco IOS commands to configure an inter-switch trunk link between Core Switch and Distribution Switch carrying VLANs 10, 20, 30."

### 2. Flawed Configuration Generated by AI
```cisco
! AI-GENERATED INSECURE CONFIGURATION
interface GigabitEthernet1/0/1
 description Trunk to DIST-BLD-A
 switchport mode trunk
 no shutdown
```

### 3. Technical & Security Analysis: Why It Was Wrong
The AI's generated trunk configuration contains two critical security and architectural defects:
1. **Unconstrained Broadcast Domain Expansion (Missing Allowed List):**
   By omitting `switchport trunk allowed vlan`, Cisco IOS defaults to carrying **all VLANs from 1 to 4094**. Broadcasts, unknown unicasts, and multicasts (BUM traffic) originating from isolated laboratory or IoT VLANs flood across the entire campus backbone into every building distribution switch, wasting backplane ASIC capacity.
2. **802.1Q Double-Tagging / VLAN Hopping Vulnerability (Default Native VLAN 1):**
   By leaving the native VLAN at default `VLAN 1`, untagged frames traverse the trunk on VLAN 1. An attacker on an access port can construct a double-tagged 802.1Q frame (outer tag VLAN 1, inner tag VLAN 10/20). When the first switch strips the outer VLAN 1 tag and forwards the frame over the trunk, the receiving switch reads the inner tag and delivers the packet into an isolated target VLAN without routing traversal (NIST SP 800-115 §5.2).

### 4. Detection Method
Detected by Invariant Verification Check **V-06** (`VLAN Safety & Native Hardening Check`) in `src/verification/service.ts`, which enforces that native VLAN 99 is explicitly set and default VLAN 1 is pruned.

### 5. Corrected Implementation
```cisco
! REMEDIATED PRODUCTION CONFIGURATION (src/configuration/renderer.ts)
interface GigabitEthernet1/0/1
 description Trunk link to DIST-BLD-A (LINK-DIST-BLD-A-CORE-01)
 switchport trunk encapsulation dot1q
 switchport mode trunk
 switchport trunk allowed vlan 10,20,30,40,50
 switchport trunk native vlan 99
 no shutdown
```
- **Allowed VLAN Pruning:** Strictly confines carried traffic to explicitly planned VLANs.
- **Native VLAN Hardening:** Configures `native vlan 99` as an unused, isolated broadcast container carrying zero user or management traffic. Default VLAN 1 is strictly disabled.

### 6. Verification & Test Evidence
Validated in `tests/unit/configuration/golden.test.ts` and `tests/unit/vlan/planner.test.ts`:
- Core switch configurations assert `switchport trunk allowed vlan 10,20,30,40,50`.
- Assert `switchport trunk native vlan 99`.
- Assert default VLAN 1 is absent from access port allocations.

## Audit Entry 3: Blind 400m Optical Reach Assumption on Multimode Fiber

### 1. Context & Original Prompt
**Prompt Given to AI:**
> "Recommend transceiver and media for an inter-facility backbone link running 380 meters with 40 Gbps required bandwidth."

### 2. Flawed Recommendation Generated by AI
> *"Recommend OM4 Multimode Fiber with 40GBASE-SR4 transceiver because 380m is less than the 400m maximum reach limit of OM4 fiber."*

### 3. Technical & Physical Layer Analysis: Why It Was Wrong
The AI made a common hallucination by decoupling **cable media type from transmission speed physics**:
- The **400-meter reach** for OM4 multimode fiber (50/125 µm, 850 nm VCSEL) is normative **strictly for 10 Gigabit Ethernet (10GBASE-SR)** per IEEE 802.3ae.
- At **40 Gigabit Ethernet (40GBASE-SR4)** per IEEE 802.3ba, chromatic and modal dispersion over 850 nm multi-mode ribbon fiber limits OM4 reach to **only 150 meters**!
- Deploying OM4 fiber over 380 meters at 40 Gbps results in optical bit error rates (BER) exceeding IEEE limits due to intersymbol interference (ISI) and total link failure. An engineered 380 m link at $\ge 40\,\text{Gbps}$ requires **OS2 Single-Mode Fiber (40GBASE-LR4)**.

### 4. Detection Method
Detected by separating **distance policy** (`src/engines/media/rules.ts`) from the **transceiver physical catalog** (`src/engines/media/transceivers.ts`), and testing bandwidth-constrained queries in `tests/unit/media/engine.test.ts`.

### 5. Corrected Implementation
```typescript
// REMEDIATED TRANSCEIVER CATALOG & VALIDATION (src/engines/media/transceivers.ts)
{
  catalogId: "om4-10g-sr",
  medium: "om4",
  standard: "10GBASE-SR",
  bandwidthGbps: 10,
  maxReachMeters: 400, // Valid ONLY at 10 Gbps
},
{
  catalogId: "om4-40g-sr4",
  medium: "om4",
  standard: "40GBASE-SR4",
  bandwidthGbps: 40,
  maxReachMeters: 150, // Correct IEEE 802.3ba modal dispersion limit
}
```
When `requiredBandwidthGbps: 40` and `runMeters: 380` are queried, the engine recognizes that OM4 exceeds reach limits and recommends **OS2 Single-Mode Fiber**.

### 6. Verification & Test Evidence
Validated in `tests/unit/media/engine.test.ts`:
- Boundary test confirms OM4 is restricted to $\le 400\,\text{m}$ for 10G.
- Runs $> 400\,\text{m}$ dynamically transition to OS2 Single-Mode Fiber (`10GBASE-LR` up to 10 km, `10GBASE-ER` up to 40 km).
